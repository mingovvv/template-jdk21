# ADR 0008: 기능 패키지 내부 구조 — api / application / domain / storage

날짜: 2026-09-03 · 상태: 채택

## 배경

package-by-feature(ADR 0001)에서 기능 패키지가 자라면 평면 구조가 한계에 부딪힌다. `order`가 14개
클래스에 도달하면서 컨트롤러·서비스·도메인·저장소·예외가 뒤섞여 보이게 됐다. 후보:
`controller/service/repository/dto/exception` 식 6분할과, 의존 방향 기준 4분할.

## 결정

기능 패키지 내부를 **의존 방향이 명확한 4개 레이어**로 나눈다:

```
order/
├── api/           # 웹 어댑터: 컨트롤러 (+ dto/ 하위에 요청/응답 DTO)
├── application/   # 유스케이스 오케스트레이션: 서비스
├── domain/        # 핵심: 모델, 리포지토리 포트(인터페이스) (+ error/ 하위에 기능 예외·ErrorCode)
└── storage/       # 영속성 어댑터: 인메모리(추후 DB) 구현
```

의존 방향은 `api → application → domain ← storage`이며 ArchUnit이 강제한다:
domain은 기능 내 어디에도 의존하지 않고, application은 api/storage를 모르며(포트 인터페이스에만 의존),
storage는 domain만 구현한다.

- 6분할 대신 4분할인 이유: 폴더가 클래스 종류가 아니라 **의존 규칙의 단위**여야 한다. dto와 controller는
  같은 규칙(웹 어댑터)을 따르므로 같은 폴더다.
- 리포지토리 인터페이스가 domain에 있는 이유: 포트는 도메인이 소유한다(ADR 0002의 "영속성 포트" 그대로).
  덕분에 application이 storage를 import하지 않는 구조가 성립한다.
- 예외·ErrorCode가 domain에 있는 이유: 실패 시나리오는 도메인 어휘다.
- 소형 기능(`ping` 등, 파일 2~3개)은 평면을 유지해도 된다. 레이어 도입 기준은 대략 7개 파일 초과 또는
  계층 간 역할 혼재가 보일 때다.
- **레이어 내부의 추가 분할은 "종류"가 아니라 "개념 군집"으로 한다.** `domain/error/`(기능의 실패 어휘:
  예외 + ErrorCode enum — 함께 변하는 응집 단위)는 허용 사례이고, `domain/enums/`·`storage/entities/`·
  `api/req·res` 같은 클래스 종류별 서랍은 만들지 않는다. 단 하나의 예외가 `api/dto/`다 — 원칙상 종류
  서랍이지만, 컨트롤러와 DTO의 동거가 주는 인지 마찰이 커서 유지보수자 가독성을 우선했다(2026-09-07 재검토).
  이 결정이 가능한 근거: 어댑터 내부 배치는 의존 방향과 무관한 컨벤션 층위라서, 아키텍처(화살표·ArchUnit
  규칙)를 건드리지 않는다. req/res 2분할은 한 엔드포인트의 입출력을 갈라놓으므로 여전히 금지. storage의 분할 기준은 저장 기술 단위다(`storage/jpa`, `storage/redis` —
  기술이 하나뿐인 동안은 나누지 않는다).
- 기능 간 의존은 기본 금지(ArchUnit)다. 기능 간 협력이 실제로 필요해지는 시점(예: 주문-쿠폰)에 공개
  진입점 방식이나 이벤트 방식을 결정하고 새 ADR과 함께 규칙을 정밀화한다.

## 결과

- 클래스를 찾는 규칙이 생겼다: "무엇을 하는 코드인가"가 아니라 "어떤 의존 규칙을 따르는 코드인가"로 찾는다.
- DB 도입 시 변경 범위가 `storage/` 안에 갇힌다 (JpaOrderRepository 추가, 인메모리 제거).
- 구조 위반은 리뷰가 아니라 ArchUnit 빌드 실패로 잡힌다.
